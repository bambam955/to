# Create "to" Directory Navigation Tool (MVP)

## Overview

This spec proposes creating "to", a modern directory navigation tool with a hybrid Go + bash architecture. Inspired by existing directory alias tools, "to" will provide a robust, extensible foundation for efficient terminal navigation with plans for future enhancements beyond basic functionality.

## What is Being Proposed

- Create a new directory navigation tool called "to" from scratch
- Implement a hybrid architecture: Go backend (`to-backend`) + bash wrapper (`to()`)
- Use JSON database format supporting multiple aliases per directory
- Provide core functionality with minimal typing: navigate (default), reg, unreg, list, clean, exp, push/pop
- Design with extensibility in mind for future features beyond basic navigation

## Why It's Needed

**Limitations of Existing Solutions:**

- Many directory navigation tools are bash-only with limited extensibility
- Plain-text storage formats restrict data structure flexibility
- Single alias per directory constraints in current implementations
- Limited metadata and analytics capabilities
- Performance issues with large alias datasets

**Benefits of "to":**

- Modern Go backend provides strong typing and robust error handling
- JSON database enables rich metadata and future extensibility
- Multiple aliases per directory without data duplication
- Clean separation of concerns for maintainability

## What Problem It Solves

- **Navigation Efficiency**: Quick access to frequently used directories
- **Organization**: Multiple logical aliases for the same physical location
- **Extensibility**: Architecture designed for future enhancements
- **Performance**: Go backend handles large datasets efficiently
- **User Experience**: Maintains familiar CLI patterns while enabling advanced features

## High-level Approach

1. **Phase 1: Foundation**
   - Set up Go project structure and CLI framework
   - Design JSON database schema with extensibility in mind
   - Create core data structures and validation logic
   - Implement configuration management (XDG compliant)

2. **Phase 2: Core Implementation**
   - Implement all database operations in Go backend
   - Create bash wrapper with communication protocol
   - Build installation system to `~/.local/bin/`
   - Add comprehensive error handling and validation

3. **Phase 3: Polish and Future-Proofing**
   - Comprehensive testing and validation
   - Documentation and installation guides
   - Architecture review for future extensibility

## Design Decisions

### Architecture: Hybrid Go + Bash

**Decision**: Hybrid architecture with Go backend and bash wrapper

**Options Considered:**

- **Pure Go**: Complete replacement with Go binary
  - Pros: Single language, consistent behavior
  - Cons: Cannot change parent shell directory, complex shell integration
- **Hybrid (chosen)**: Go backend + bash wrapper
  - Pros: Leverages shell's `cd` capability, clean separation, maintainable
  - Cons: Two languages, communication overhead

**Rationale**: The fundamental `cd` limitation makes hybrid architecture the only practical approach while providing clean separation of concerns.

### Database Format: JSON

**Decision**: JSON database with extensible schema

**Options Considered:**

- **Plain text**: Simple but restrictive
  - Pros: Human-readable, zero parsing overhead
  - Cons: No metadata, limited structure, hard to extend
- **SQLite**: Powerful but overengineered
  - Pros: Rich querying, ACID properties
  - Cons: Complex setup, overkill for simple use case
- **JSON (chosen)**: Balanced approach
  - Pros: Structured, extensible, human-readable, versionable
  - Cons: Parsing overhead, requires careful schema design

**Rationale**: JSON provides the right balance of structure, extensibility, and readability while avoiding database complexity.

### Communication Protocol: Special Output Format

**Decision**: `[to] <path>` prefix for navigation output

**Options Considered:**

- **Exit codes**: Standard but limited information
  - Pros: Unix standard, simple
  - Cons: Cannot convey rich error information
- **JSON responses**: Structured but verbose
  - Pros: Rich information, extensible
  - Cons: Verbose, parsing complexity
- **Special prefix (chosen)**: Simple and clear
  - Pros: Easy parsing, clear separation, human-readable
  - Cons: Custom protocol, limited to simple responses

**Rationale**: Special prefix provides clean separation between navigation commands and user messages while maintaining simplicity.

### Installation Strategy: User-Local

**Decision**: Install to `~/.local/bin/`

**Options Considered:**

- **System-wide**: `/usr/local/bin/`
  - Pros: Available to all users, standard location
  - Cons: Requires sudo, system administration overhead
- **Package managers**: Homebrew, apt, etc.
  - Pros: Standard installation method
  - Cons: Multi-platform complexity, maintenance burden
- **User local (chosen)**: `~/.local/bin/`
  - Pros: No sudo required, follows XDG conventions, simple
  - Cons: User must ensure PATH includes `~/.local/bin`

**Rationale**: User-local installation follows modern practices and avoids system administration complexity.

## CLI Design Principles

**Minimal Typing:**

- Navigation uses default command: `to <alias>`
- Short command names: `reg`, `unreg`, `list`, `clean`, `exp`
- Push/pop: `to -p <alias>`, `to -o`
